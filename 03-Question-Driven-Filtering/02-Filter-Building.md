# Wireshark Filter Building

## Objective

The goal of this file is to make display-filter construction a practical skill rather than a memorization exercise.

By the end of this workflow, you should be able to:

* Start with an investigation question.
* Identify the packet field that can answer it.
* Discover the correct Wireshark field name.
* Select the appropriate operator.
* Construct the filter incrementally.
* Combine multiple conditions safely.
* Test whether the filter behaves as expected.
* Diagnose syntax errors and unexpected zero-result filters.
* Build filters for common protocols and investigation scenarios.
* Avoid writing unnecessarily large or fragile filters.

The core workflow is:

```text
Question
    ↓
What evidence would answer it?
    ↓
Which packet field contains that evidence?
    ↓
What field type is it?
    ↓
Which operator is appropriate?
    ↓
Build a simple filter
    ↓
Test it
    ↓
Add conditions progressively
    ↓
Validate the result
```

---

## The Filter-Building Mindset

Do not begin with:

```text
"What complicated filter can I write?"
```

Begin with:

```text
"What exactly am I trying to find?"
```

For example:

```text
Question:
Which packets came from 192.168.1.10?
```

Translate the question:

```text
Evidence:
Source IPv4 address

Field:
ip.src

Condition:
Equals 192.168.1.10
```

Result:

```text
ip.src == 192.168.1.10
```

The important skill is not memorizing the final expression.

The important skill is being able to derive it.

---

## Step 1 — Define the Investigation Question

Write the question in plain language before constructing the filter.

Examples:

```text
Which packets originated from this host?
Which packets were sent to this server?
Which TCP connections used port 443?
Which DNS queries were generated by this client?
Which HTTP requests returned errors?
Which TCP packets were retransmitted?
Which packets contain a specific hostname?
```

Avoid vague questions such as:

```text
Show suspicious traffic.
Show bad packets.
Show interesting packets.
```

Convert vague questions into observable evidence.

For example:

```text
Vague:
Show suspicious DNS traffic.

Better:
Show DNS queries for a specific domain.

Better:
Show repeated DNS queries from one client.

Better:
Show DNS responses containing a specific response code.
```

A useful question should identify something that Wireshark can actually observe.

---

## Step 2 — Identify the Evidence

Ask:

```text
What packet information would answer the question?
```

Common evidence categories include:

| Question               | Evidence               |
| ---------------------- | ---------------------- |
| Who sent it?           | Source address         |
| Who received it?       | Destination address    |
| Which protocol?        | Protocol fields        |
| Which service?         | TCP/UDP port           |
| Which TCP event?       | TCP flags              |
| Which DNS name?        | DNS name fields        |
| Which HTTP resource?   | HTTP request fields    |
| Which TLS server name? | TLS handshake metadata |
| When did it happen?    | Packet timestamp       |
| Which packet?          | Packet number          |
| Does a field exist?    | Field existence        |

This step prevents random filter construction.

---

## Step 3 — Find the Correct Field

Wireshark display filters operate on protocol fields.

You therefore need to identify the field containing the evidence you want.

For example:

```text
Source IPv4 address
```

can be represented by:

```text
ip.src
```

A TCP destination port can be represented by:

```text
tcp.dstport
```

A DNS query name can be represented by a DNS name field such as:

```text
dns.qry.name
```

The exact field matters.

Do not assume that a human-readable label is automatically the correct filter field.

---

## Discover Fields from the Packet Details Pane

A practical way to learn fields is to inspect an actual packet.

Select a packet and expand its protocol layers.

For example:

```text
Internet Protocol Version 4
    Source Address: 192.168.1.10
    Destination Address: 192.168.1.20
```

Right-click a relevant field and use Wireshark's filtering/context-menu options to discover how Wireshark represents that field.

This is often faster and safer than guessing field names.

## Protocol Fields vs Generic Fields

Some fields belong directly to a protocol.

Examples:

```text
ip.src
ip.dst

tcp.srcport
tcp.dstport

udp.srcport
udp.dstport

dns.qry.name
```

Other useful filter expressions operate on broader packet properties.

Examples include:

```text
frame.number
frame.time
frame.len
```

The important distinction is:

```text
Protocol-specific evidence
        vs.
Packet/frame-level evidence
```

Choose the field that most directly represents the question.

---

## Understand the Field Type

Before choosing an operator, determine what kind of value the field contains.

Common categories include:

```text
Address
Integer
Boolean
String
Protocol
Time
Flags
```

The field type influences how you should construct the comparison.

For example:

```text
IP address
```

is different from:

```text
TCP port number
```

and both are different from:

```text
HTTP request method
```

Do not treat every field as a string.

---

## Equality

Use equality when you want an exact match.

Example:

```text
ip.src == 192.168.1.10
```

Meaning:

```text
Show packets whose IPv4 source address is exactly 192.168.1.10.
```

Another example:

```text
tcp.dstport == 443
```

Meaning:

```text
Show packets whose TCP destination port is 443.
```

Equality is one of the most useful building blocks for precise filters.

---

## Inequality

Use inequality when you want to exclude an exact value.

Example:

```text
ip.src != 192.168.1.10
```

This means:

```text
Show packets whose IPv4 source address is not 192.168.1.10.
```

Be careful with negative conditions.

For example:

```text
tcp.dstport != 443
```

does not mean:

```text
Show all non-HTTPS traffic.
```

It only means:

```text
Show packets where the TCP destination port is not 443.
```

Traffic may still use HTTPS on another port.

Always interpret the filter literally.

---

## Field Existence

Sometimes the question is not:

```text
What is the value?
```

but:

```text
Does this field exist in the packet?
```

A field-existence test is useful when looking for packets that contain a particular protocol field or feature.

For example:

```text
tcp.options
```

can be used to identify packets where the corresponding TCP field is present.

Field existence is particularly useful when:

* looking for protocol features
* locating specific packet types
* narrowing a large capture
* investigating optional protocol fields

Do not confuse field existence with a specific value comparison.

---

## String Matching

String fields can often be examined using operators appropriate to textual data.

For example:

```text
http.request.method == "GET"
```

asks for HTTP requests whose method is exactly `GET`.

For a textual investigation, you may also need substring or regular-expression matching where supported and appropriate.

The important distinction is:

```text
Exact value
```

versus:

```text
Value contains a pattern
```

For example:

```text
Exact:
http.request.method == "GET"
```

is different from a filter intended to find text containing a particular word.

Use the narrowest operation that answers the actual question.

---

## Numeric Comparisons

Numeric fields can be compared using relational operators.

Common operators include:

```text
==
!=
>
<
>=
<=
```

For example:

```text
tcp.window_size_value == 0
```

can help locate TCP packets advertising a zero receive window.

Another example:

```text
frame.len > 1400
```

can identify packets larger than 1400 bytes.

The important point is that numeric comparisons should be based on numeric meaning rather than string matching.

---

## Address Filtering

Address filtering is one of the most common Wireshark tasks.

### Source Address

```text
ip.src == 192.168.1.10
```

Question:

```text
Which IPv4 packets came from this host?
```

### Destination Address

```text
ip.dst == 192.168.1.20
```

Question:

```text
Which IPv4 packets were sent to this host?
```

### Either Direction

If the question is:

```text
Which IPv4 packets involve 192.168.1.10?
```

construct the logic explicitly:

```text
ip.addr == 192.168.1.10
```

This is different from using only:

```text
ip.src
```

or:

```text
ip.dst
```

Understand the direction represented by each field before filtering.

---

## Source vs Destination Is an Investigative Decision

Consider:

```text
ip.src == 192.168.1.10
```

This answers:

```text
Who sent the packet?
```

While:

```text
ip.dst == 192.168.1.10
```

answers:

```text
Who received the packet?
```

The difference becomes critical during investigations.

For example:

```text
Which server did the client contact?
```

may require examining:

```text
ip.dst
```

while:

```text
Which client generated these requests?
```

may require:

```text
ip.src
```

Do not use `ip.addr` automatically when direction matters.

---

## Port Filtering

Ports can help identify traffic associated with a service.

Examples:

```text
tcp.port == 443
```

```text
udp.port == 53
```

```text
tcp.dstport == 22
```

```text
tcp.srcport == 8080
```

Think about the direction.

For example:

```text
tcp.dstport == 443
```

means:

```text
TCP traffic directed toward destination port 443.
```

While:

```text
tcp.srcport == 443
```

means:

```text
TCP traffic originating from source port 443.
```

---

## Protocol Filtering

Protocol-level filters are useful for reducing a large capture quickly.

Examples:

```text
tcp
```

```text
udp
```

```text
dns
```

```text
http
```

```text
tls
```

```text
icmp
```

Start broad when you do not yet know what is happening.

For example:

```text
dns
```

can reduce a large capture to DNS traffic before you investigate:

```text
Who generated the queries?
Which names were queried?
What responses were returned?
```

## TCP Flag Filtering

TCP flags are valuable for connection analysis.

For example, to investigate SYN packets:

```text
tcp.flags.syn == 1
```

To investigate packets with the ACK flag:

```text
tcp.flags.ack == 1
```

To investigate resets:

```text
tcp.flags.reset == 1
```

To investigate FIN packets:

```text
tcp.flags.fin == 1
```

The key skill is translating a TCP event into the corresponding field condition.

For example:

```text
Question:
Which packets indicate a TCP reset?
```

Translate:

```text
TCP reset
    ↓
TCP RST flag
    ↓
tcp.flags.reset
    ↓
tcp.flags.reset == 1
```

---

## Combining Conditions with AND

Use `&&` when all conditions must be true.

Example:

```text
ip.src == 192.168.1.10 && tcp.dstport == 443
```

Meaning:

```text
Show packets that:
1. came from 192.168.1.10
2. use TCP destination port 443
```

This is useful for narrowing a broad result.

Think:

```text
A AND B
```

means:

```text
A must be true
AND
B must also be true
```

---

## Combining Conditions with OR

Use `||` when either condition can be true.

Example:

```text
tcp.dstport == 80 || tcp.dstport == 443
```

Meaning:

```text
Show packets directed to TCP port 80 or TCP port 443.
```

Think:

```text
A OR B
```

means:

```text
A can be true
OR
B can be true
```

Use OR when several alternatives belong to the same investigative question.

---

## Using NOT

Use `!` when you need to exclude a condition.

Example:

```text
!arp
```

Meaning:

```text
Exclude packets identified as ARP.
```

Another example:

```text
!(tcp.port == 443)
```

The important rule is to understand exactly what is being negated.

When a condition becomes complex, use parentheses.

---

## Parentheses and Logical Grouping

Parentheses make filter logic explicit.

Consider:

```text
ip.src == 192.168.1.10 && tcp.dstport == 80 || tcp.dstport == 443
```

This can become difficult to reason about.

Instead, group the intended alternatives:

```text
ip.src == 192.168.1.10 && (tcp.dstport == 80 || tcp.dstport == 443)
```

Now the logic is clear:

```text
Source must be 192.168.1.10

AND

Destination port must be either:
80
OR
443
```

When a filter contains multiple logical operators, use parentheses whenever they make the intended logic clearer.

---

## Build Filters Progressively

Do not immediately construct a complicated expression.

Suppose the investigation question is:

```text
Which HTTPS-related TCP traffic came from 192.168.1.10?
```

Start with:

```text
tcp
```

Then:

```text
tcp.port == 443
```

Then:

```text
ip.src == 192.168.1.10 && tcp.port == 443
```

Each step gives you an opportunity to verify your assumptions.

This is safer than immediately typing a long filter.

---

## Progressive Construction Example

Investigation:

```text
Find DNS traffic from one client.
```

Start:

```text
dns
```

Then:

```text
dns && ip.src == 192.168.1.10
```

Then perhaps narrow further:

```text
dns && ip.src == 192.168.1.10 && dns.qry.name == "example.com"
```

At every stage ask:

```text
Did the result change as expected?
Does the remaining traffic make sense?
Did I accidentally exclude useful packets?
```

## DNS Filter Construction

DNS investigations commonly begin broadly.

Start:

```text
dns
```

Then identify the relevant question.

### Find Queries

```text
dns.flags.response == 0
```

This separates DNS queries from DNS responses.

### Find Responses

```text
dns.flags.response == 1
```

### Filter a Specific Query Name

```text
dns.qry.name == "example.com"
```

### Combine Client and Query

```text
ip.src == 192.168.1.10 && dns.qry.name == "example.com"
```

The exact fields available depend on the packet and protocol dissection.

Inspect the packet before assuming a field exists.

## HTTP Filter Construction

Begin with:

```text
http
```

Then determine what you want to investigate.

### HTTP GET Requests

```text
http.request.method == "GET"
```

### HTTP POST Requests

```text
http.request.method == "POST"
```

### Requests to a Specific Host

```text
http.host == "example.com"
```

### Combine Host and Method

```text
http.host == "example.com" && http.request.method == "POST"
```

The workflow remains:

```text
Protocol
    ↓
Relevant field
    ↓
Exact condition
    ↓
Additional condition if necessary
```

## TLS Filter Construction

TLS traffic is often visible even when application contents are encrypted.

Start with:

```text
tls
```

Then inspect the TLS handshake and determine which metadata is available.

Depending on the capture, useful fields may include:

```text
tls.handshake.type
tls.handshake.version
tls.handshake.extensions_server_name
```

For example, a filter targeting the Server Name Indication field may be constructed from the field shown by Wireshark's packet details/autocomplete.

Do not assume that encrypted traffic is invisible.

Instead distinguish:

```text
Encrypted application contents
```

from:

```text
Visible protocol metadata
```

---

## Time-Based Filtering

Time can be useful when the investigation already has a known incident window.

For example:

```text
frame.time
```

can be inspected and used when constructing time-based conditions.

A practical workflow is:

```text
Determine incident time
        ↓
Locate packets around that period
        ↓
Identify relevant protocol
        ↓
Apply protocol filter
        ↓
Apply host/service conditions
```

Do not make time filtering unnecessarily complicated if packet-number or protocol-based narrowing is easier.

---

## Packet Number Filtering

Packet numbers are useful when you have already identified an important packet.

Example:

```text
frame.number == 150
```

This can help you return to a specific packet while documenting an investigation.

Packet numbers are especially useful for:

* evidence references
* investigation notes
* comparing nearby packets
* returning to a known event

A packet number is an evidence reference, not an explanation of what happened.

```text
How Wireshark expresses the condition
```

After generating a filter from the UI, inspect it instead of treating it as magic.

## Use Autocomplete to Verify Fields

If you think the field is:

```text
dns.qry.name
```

type:

```text
dns.qry.
```

into the display-filter bar.

Confirm that Wireshark offers the expected field.

This prevents errors such as:

```text
dns.query.name
dns.query
dns.name
```

when the actual field is different.

Field discovery should come from Wireshark rather than memory whenever you are uncertain.

---

## Debugging Syntax Errors

If Wireshark rejects a filter, do not randomly modify characters.

Break the filter apart.

Suppose this fails:

```text
ip.src == 192.168.1.10 && tcp.dstport == 443 && dns.qry.name == "example.com"
```

Test:

```text
ip.src == 192.168.1.10
```

Then:

```text
tcp.dstport == 443
```

Then:

```text
dns.qry.name == "example.com"
```

Then combine them.

This identifies which component caused the problem.

---

## Debugging Zero Results

A syntactically valid filter can still produce zero packets.

That does not automatically mean the filter is wrong.

Possible explanations:

```text
The capture contains no matching traffic.
The field is absent from the relevant packets.
The value is different from what you expected.
The traffic uses another protocol.
The direction is wrong.
The port is different.
The packet is encrypted.
The protocol was not dissected as expected.
The capture begins after the event.
```

Use a broad-to-narrow process.

For example:

```text
dns
```

If results exist, continue:

```text
dns && ip.src == 192.168.1.10
```

If results exist, continue:

```text
dns && ip.src == 192.168.1.10 && dns.qry.name == "example.com"
```

If the final filter returns nothing, determine which assumption removed the packets.

---

## Distinguish No Matches from Wrong Logic

These are different problems.

### No Matches

The filter may be correct, but the capture may not contain the event.

### Wrong Logic

The filter may be syntactically valid but represent the wrong investigative condition.

Example:

```text
tcp.srcport == 443
```

may not answer:

```text
Which client connections targeted HTTPS?
```

The better question may require examining:

```text
tcp.dstport == 443
```

or:

```text
tcp.port == 443
```

depending on the investigation.

Always compare the filter against the original question.

---

## Test Filter Logic Against Known Packets

Before trusting a complicated filter, find a packet that you know should match.

Then ask:

```text
Does my filter select it?
```

Also find a packet that should not match.

Ask:

```text
Does my filter exclude it?
```

This creates a simple validation process:

```text
Known positive
      ↓
Should match
      ↓
Apply filter
      ↓
Confirm

Known negative
      ↓
Should not match
      ↓
Apply filter
      ↓
Confirm
```

This is particularly useful for complex logical expressions.

---

## Avoid Overly Broad Filters

A filter such as:

```text
tcp
```

may return thousands of packets.

That is sometimes useful as a first step.

But if your question is:

```text
Which TCP connections from one client targeted port 443?
```

you should narrow it.

For example:

```text
ip.src == 192.168.1.10 && tcp.dstport == 443
```

The objective is not to make every filter extremely narrow.

The objective is to make the filter appropriate for the current question.

---

## Avoid Overly Complicated Filters

A filter containing dozens of conditions is difficult to validate.

Prefer:

```text
broad filter
    ↓
observe
    ↓
narrow filter
    ↓
observe
    ↓
specific filter
```

over:

```text
one giant expression
```

This makes the investigation easier to understand and document.

---

## Avoid Confusing Ports with Protocols

Do not assume:

```text
tcp.port == 443
```

proves that the traffic is HTTPS.

It tells you that TCP port 443 is involved.

The actual protocol identification should come from packet dissection and evidence.

Likewise:

```text
tcp.port == 22
```

does not by itself prove that the application is SSH.

Ports are useful indicators, not absolute protocol identity.

---

## Avoid Confusing Address Presence with Direction

Compare:

```text
ip.addr == 192.168.1.10
```

with:

```text
ip.src == 192.168.1.10
```

The first asks:

```text
Does this address participate in the IPv4 packet?
```

The second asks:

```text
Was this address the source?
```

Use the directional field when direction matters.

---

## Avoid Assuming Every Packet Has Every Field

A filter involving:

```text
tcp.dstport
```

only applies meaningfully to packets containing the relevant TCP field.

A DNS field will not appear in an ordinary ARP packet.

Think in terms of protocol layers:

```text
Ethernet
   ↓
IP
   ↓
TCP
   ↓
Application protocol
```

A field becomes available only when the corresponding protocol structure is present and successfully dissected.

---

## Filter Construction Workflow

Use this workflow whenever building a new filter.

```text
1. Define the question.

2. Identify the evidence needed.

3. Find the packet field containing that evidence.

4. Verify the field name in Wireshark.

5. Determine the field type.

6. Select the appropriate operator.

7. Build the simplest possible filter.

8. Test the result.

9. Add one condition at a time.

10. Use parentheses when logic becomes complex.

11. Validate against known packets.

12. Interpret the resulting traffic.
```

Do not skip directly from:

```text
Question
```

to:

```text
Long filter
```

The intermediate reasoning is part of professional packet analysis.

## Filter Debugging Checklist

When a filter does not behave as expected, ask:

```text

[ ] Do I need parentheses?
[ ] Does the capture actually contain the event?
[ ] Is the protocol encrypted?
[ ] Was the packet dissected as expected?
[ ] Did a previous condition remove the packets?
```

## Filter Construction Decision Framework

When faced with a new filtering problem, use:

```text
What am I looking for?
        ↓
What packet evidence represents it?
        ↓
Where is that evidence?
        ↓
What is the field name?
        ↓
What type of field is it?
        ↓
What operator expresses my question?
        ↓
What value should match?
        ↓
Do I need direction?
        ↓
Do I need another condition?
        ↓
Do I need AND / OR / NOT?
        ↓
Do I need parentheses?
        ↓
Test
        ↓
Validate
```

If you cannot explain every part of your filter, you probably built it too quickly.

## Professional Filter-Building Habits

Develop these habits:

```text
Start from a question.
Use packet evidence.
Discover fields rather than guessing.
Build progressively.
Keep expressions readable.
Use direction intentionally.
Use parentheses for complex logic.
Validate against known packets.
Treat zero results as information.
Do not confuse ports with protocol identity.
Do not interpret a filter result without context.
```

A professional filter is not necessarily a complicated filter.

A professional filter is one that clearly answers a defined investigative question and can be explained and validated.
